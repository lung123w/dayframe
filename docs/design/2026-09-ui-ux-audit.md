# DayFrame UI/UX audit + direction concepts (2026-09)

*Prepared by `df-analyst`. Every claim in §2–§6 cites `path:line` against `origin/master` `526f3b3` (the released line). Read-only; no code, DB or `.dev_context/` file was modified.*

## 1. Scope & method

**Deliverable.** A code-grounded audit of DayFrame's current interface, plus three candidate design directions with build cost, so a single direction can be chosen before any restyle work is scheduled.

**Method.** (1) Read Anderson's own design brief at `.opencode/design-references/notion-stripe-2026.md` (the "craft floor": one accent, hairline borders, no pill buttons, a real type scale, no emoji chrome). (2) Read `.dev_context/ARCHITECTURE.md`, `DATA_MODEL.md`, `ROUTE_MAP.md`, `DECISION_LOG.md` (all dated 2026-09-20, verified against `master` `526f3b3`). (3) Read the prior planner/goals design notes in `docs/plans/` so already-settled decisions are not re-litigated. (4) Read the code: `src/index.css`, `src/App.css`, `src/App.jsx`, `src/api.js`, and all 28 `src/components/*.jsx` / `*.css` pairs; then measured the stylesheets mechanically (counts of colours, type sizes, radii, transitions, breakpoints, `:focus`/`:hover` rules, orphaned files and unreferenced class names).

**Counting basis.** `src/components/` holds 28 `.jsx` and 28 `.css` files; 24 components are live and 4 are imported by nothing (verified by grep for importers: `Calendar`, `DailyShutdown`, `DayPanel`, `OutstandingTasks`). Stylesheet volume: 5,891 CSS lines in the files that are actually loaded (`src/index.css`, `src/App.css`, 24 component stylesheets) plus 1,828 lines in stylesheets belonging only to those 4 dead components — 7,719 total. Application code: ~9,011 lines across `App.jsx`, the 28 components, `utils/` and `api.js`.

**Severity key.** **H** = costs the user data, time or trust today; **M** = an ongoing friction or inconsistency; **L** = cosmetic or housekeeping.

**What this document is not.** It is not a stack recommendation, a colour palette or a type scale — those belong to the pitch deck. §7–§9 deliberately describe direction, mechanism and scope without naming values, libraries or frameworks.

## 2. The app as it is today

**Views.** Six, selected by a single state string `activeView`, with no router: `planner` (default), `today`, `habits`, `projects`, `review`, `finance` (`src/App.jsx:41`, `:330-426`; navigation in `src/components/Sidebar.jsx:13-77`). `activeView` defaults to **`planner`, not `today`** (`src/App.jsx:41`).

**Shell.** A two-box flex layout: a fixed 220px dark rail (`src/components/Sidebar.css:1-13`) and a scrolling main panel offset by `margin-left: 220px` with 20/24px padding (`src/App.css:28-43`). The rail carries a brand block, a 6-item "VIEWS" group and a 2-item "TOOLS" group (Notifications, Backup). There is no breadcrumb, no page title outside each view's own header, and no way to reach a view other than the rail.

**Global styles.** Two global files: `src/index.css` (53 lines, imported by `src/main.jsx:3`) and `src/App.css` (335 lines, imported by `src/App.jsx:17`), plus one co-located stylesheet per component. There is no token layer — `:root` in `src/index.css:3-16` declares no colour, spacing, radius or type variables, and the only custom property anywhere is `--habit-color`, set inline per cell (`src/components/HabitHeatmap.jsx:107`). Typography is a Google Fonts `@import` of Plus Jakarta Sans (`src/index.css:1`), so the "local-first" app's type depends on the network; the same font stack is then re-declared on `body` and on individual button rules (`src/index.css:4`, `src/App.css:21`, `src/App.css:138`, `:173`, `:198`, `:215`).

**Data access.** One `fetch` call site — `request()` in `src/api.js:1-12` — mounted on 16 service objects (`src/api.js:14-172`). No component calls `fetch` directly. Cross-view state lives entirely in `App.jsx` (tasks, projects, subtasks, `todayOrder`, keyEvents, financialCards, monthlyReviews, modal flags: `src/App.jsx:31-45`), and `loadData()` re-fetches **all seven collections in parallel** (`src/App.jsx:47-78`) after almost every mutation. Three views bypass that: `HabitTracker` fetches its own data and receives no props (`src/components/HabitTracker.jsx:31-71`), `PlannerHabitsPanel` likewise (`src/components/PlannerHabitsPanel.jsx:21-49`), and `DailyWorkflow` fetches its own (`src/components/DailyWorkflow.jsx:12-23`).

**Ordering.** There are four competing orderings. Root sort is dueDate→priority (`src/App.jsx:19-28`). The planner's day columns sort by `scheduledTime`→`sortOrder`→priority (`src/components/DayColumn.jsx:97-117`). The backlog sorts by priority→`createdAt` (`src/components/BacklogSidebar.jsx:47-53`). The Today list is ordered by the persisted `todayOrder` array via `mergeOrder` (`src/components/TodayView.jsx:92-95`), stored as a generic settings row (`src/App.jsx:202-211`) of string keys that are either `"400"` or `"400-2026-09-21"` for recurring instances (`src/components/TodayView.jsx:26-28`).

**Period model.** Monday-start weeks are computed at run time (`src/components/DailyPlanner.jsx:36`, `src/components/WeeklyReview.jsx:292-294`, `src/components/MiniWeekBar.jsx:9-14`); habit entries are keyed `(habitId, date)`; monthly reviews are keyed `YYYY-MM` and any month that is not the current one is read-only (`src/components/MonthlyReview.jsx:218-219`). This matches ADR-004/005.

**What the interface does not have today.** No dark mode (`color-scheme: light` only, `src/index.css:8`; zero `prefers-color-scheme` rules anywhere). No component or styling system beyond hand-written CSS. No icon set beyond Font Awesome glyphs lifted from `react-icons` (`src/components/Sidebar.jsx:2`). No save indicator anywhere except one (`src/components/YearlyGoals.jsx:155`). No empty-state design: every empty surface is one of a handful of ad-hoc strings (`src/components/DayColumn.jsx:357-369`, `src/components/BacklogSidebar.jsx:126-133`). No keyboard layer (see F08, §5). No print or export stylesheet (0 `@media print`), the only export being a JSON download (`src/App.jsx:281-317`). No responsive navigation: below 768px the rail is `display: none` (`src/components/Sidebar.css:94-98`) and nothing replaces it.

## 4. The daily planning loop: capture → schedule → execute → review

Traced through the code, with the interactions each step actually costs. "Click" means a pointer action; a drag counts as press + move + release.

### 4.1 Capture

Three entry points exist, none of them global.

1. **Today quick capture** — `src/components/TodayView.jsx:347-358`. One click into the input, type, Enter. The handler (`:39-49`) posts `{title, dueDate: today, status:'pending'}` (`:43`) — no project, no priority, no time, no recurrence. The input has **no autofocus and no hotkey**, and it lives inside the "Today" section, which is the middle column of a three-column layout (`src/components/TodayView.css:83-112`). On Enter the whole app re-fetches seven collections (`src/App.jsx:128` → `:47-78`).
2. **Task modal** — opened by *New Task* on Today (`src/components/TodayView.jsx:308`), on the planner toolbar (`src/App.jsx:348`), or by any day column's add button (`src/components/DayColumn.jsx:344-353`, `:400-402`). The due date is prefilled from `selectedDate` (`src/components/TaskModal.jsx:175-188`), then the full 11-field form. Two clicks plus typing plus Save.
3. **Backlog** — *none*. `src/components/BacklogSidebar.jsx:73-123` renders a title, a count, a two-way view toggle, a search box and a project `<select>`. There is no way to add a task from the planner's own inbox.

**Cost, cold open → a task on today:** 1 click (Today in the rail) + 1 click (capture input) + typing + 1 Enter = **3 pointer actions**, or 2 clicks + Save via the modal. Reachable only from Today; from the planner (the default view, `src/App.jsx:41`) it is 1 click away plus the above.

### 4.2 Schedule

- **Backlog → a day**: HTML5 drag only. The backlog row sets a JSON payload on `dragstart` (`src/components/BacklogSidebar.jsx:68-71,150-151`); the drop is handled in the planner (`src/components/DailyPlanner.jsx:67-112`) and lands as `PUT /api/tasks/:id {dueDate}` (`src/App.jsx:214-222`). The grip icon is decorative and has no accessible name (`src/components/BacklogSidebar.jsx:153`). **No button, no keyboard path.**
- **Cross-day move**: the same drag (`src/components/DailyPlanner.jsx:104-107`).
- **Reorder inside a planner day**: drag a card onto another; `handleTaskDragOver` recomputes an insertion index on **every** `dragover` event (`src/components/DayColumn.jsx:144-151`), the drop writes `PUT /api/tasks/:id {sortOrder}` for each task whose index changed (`src/components/DailyPlanner.jsx:93-97`), and if the column is today it also rewrites `todayOrder` (`:100-103`).
- **Reorder inside Today**: drag, or the up/down buttons (`src/components/TodayView.jsx:110-116`) — which are `opacity: 0` until hover (`src/components/TodayView.css:369-381`, F10).
- **Overdue → today**: *Pull to today* (`src/components/TodayView.jsx:85-89`, F29) or dragging the overdue card onto the Today section (`:131-142`).

**Cost, backlog → today:** 1 drag (4 pointer events) per task. For five tasks, five drags; for the same five, "Pull to today" is one click but reschedules everything overdue, not a subset.

### 4.3 Execute

- **Complete a task**: one click on the status button, Today (`src/components/TodayView.jsx:181-197`) or planner (`src/components/DayColumn.jsx:222-228` → `STATUS_CYCLE` `:8-13` → `src/App.jsx:152-184`, which writes `statusOverrides`/`statusFromOverrides` for recurring instances rather than the base row). No keyboard equivalent anywhere.
- **Log a habit**: click *Mark Done* → popover opens → type minutes → Save or Enter (`src/components/PlannerHabitsPanel.jsx:116-138` + `src/components/TimePopover.jsx:42-56`), or the same from a heat-map cell (`src/components/HabitHeatmap.jsx:122-132`) — the cell popover is positioned off the cell's right edge with no viewport clamping (`:130`). On the Habits view the same flow exists plus a manual minutes box whose value is shared across every card on the page (F23).
- **Read the day**: the timeline (`src/components/DailyTimeline.jsx`) shows 06:00–21:00, is 220px wide (`src/components/DailyTimeline.css:2`), clips anything outside its window (F18) and cannot be interacted with (F19). The one useful affordance it has is the current-time rule (`:121-127`).

**Cost, habit logged:** 3–4 interactions. **Cost, task completed:** 1 click (mouse only).

### 4.4 Review

- Reached with 1 click (Review in the rail). The screen opens on the week containing **yesterday** (`src/components/WeeklyReview.jsx:292-294`) with the plan week in its header (`:583`) and the *reviewed* week on the habit chips (`:716`).
- The cleanup checklist does not come from the user's tasks: it is a 7-item template hard-coded in the component (`src/components/WeeklyReview.jsx:33-44`) seeded whenever a week has no saved tasks (`:348-350`).
- The only bridge from review into the planner is "Write weekly goals to DayFrame" (`:507-539`), which **replaces** the planner's weekly objectives and asks first with a `window.confirm` when they exist.
- There is **no close-out step**. `DailyShutdown.jsx` — a designed end-of-day surface that reads and writes `daily_notes` (`:18-46`) — is imported by nothing (F42), so the loop from "execute" back to "plan tomorrow" has no surface at all.
- Finance is a separate monthly loop with its own read-only rule (`src/components/MonthlyReview.jsx:218-219,544-548`) and does not touch the daily loop.

### 4.5 Friction and dead ends, ranked

1. The loop is split across **two views with three orderings** (§2), so "what am I doing today" has two different answers on two screens.
2. **Every scheduling action is drag-only** (§4.2), and drag is the interaction with no keyboard path, no accessible name and the weakest touch story.
3. **Ordering is the user's manual work** (F33) and it does not survive the trip from Today to the planner.
4. **Writing anything long is unconfirmed and per-keystroke** (F25, F26).
5. **The review is one screen showing two weeks** (F35).
6. **Two controls that look like navigation do nothing** (F20), and one of them was explicitly required to keep working by a prior design (`docs/plans/2026-03-22-planner-ux-design.md:104-114`).
7. **The day's end has no surface** (F42), so the loop never closes.

## 7. Concept A — Calm Canvas

*Calm and minimalist: whitespace, a soothing neutral canvas, restrained type, zero clutter. The closest of the three to Anderson's own reference — deliberately so, because it is the cheapest and the lowest-risk.*

### Layout idea

At 1440×900: no permanent dark rail. A single 52px top strip carries the app name at the left, the day's date as the page title beside it, and four text destinations (Today · Week · Habits · Review) at the right, plus a "More" overflow holding Finance, Projects, Backup and Notifications. Below it, one column, centred, capped at roughly 720px of text and 900px of content: the day in reading order. The bottom half of the screen is the day list — one line per task, separated by hairlines rather than boxes, no card backgrounds, no shadows. Each line is: a completion circle, the title at body size, and right-aligned metadata in one muted size (project dot, time if set). Hovering a line reveals exactly two controls — move and defer — as text, not icon buttons. The habit rail is a right-hand column about 260px wide, collapsed to a single "6 of 8 done" line until clicked. The day's timeline becomes a thin vertical strip of hour marks alongside the list (a reading of the day, not a second interface), and the week becomes a horizontal band of seven hairline-divided columns with no per-day boxes: empty days are simply quiet space. One accent colour, reserved for state (active destination, completed items, the current hour). Everything else is neutral.

### Navigation flow (cold open → "what do I do now")

Cold open is **Today**, not the planner. Steps for the four common cases:

- **Add a task**: the capture line is the first element under the title, always present, focused by clicking it or by pressing `/`. Type, press Enter. **1 keystroke to focus, 1 to commit.** New tasks inherit the last-used project.
- **Move a task onto today**: open *Week*, the backlog is the left band with a one-line add; each backlog row carries an inline "Today" text action. **1 click.** Dragging still works for people who prefer it.
- **Log a habit**: the right rail shows each habit as a row with a single completion control. **1 click** logs "done" with zero minutes; hovering (or focusing) the row's time field allows an exact duration for the habits that care.
- **Get to today's plan**: it is the cold open — **0 clicks**.

### Key highlights

- Today is the cold open; the week view becomes a reference surface, not a second planner (`src/App.jsx:41` changes).
- One capture line, present on every view, with a focus hotkey, inheriting the last-used project and priority (`src/components/TodayView.jsx:43`).
- Task rows replace task cards: hairline separators, no per-row border-left colour stripe, no card backgrounds (`src/components/TodayView.css:192-234`).
- Hover/focus reveals are replaced by two persistent-in-focus text actions per row, so reorder and defer survive on touch and keyboard (`src/components/TodayView.css:369-381,447-491`).
- The habit rail logs in one click, with the duration as an optional refinement rather than a prerequisite (`src/components/PlannerHabitsPanel.jsx:116-138`).
- One type ladder of three sizes (label, body, title) replacing the 13 current px values (`§3` F05).
- The week bar's day buttons actually select a day (they currently call an empty function, `src/components/DailyPlanner.jsx:140`).
- Saves become visible: a single discreet "Saved" / "Could not save" line that occupies the same space, replacing per-keystroke writes with a debounced save (`src/components/WeeklyReview.jsx:366-382`).

### Feature implications

- **Today** — Rebuilt around the list-plus-rail composition; becomes the cold open and the only capture surface.
- **Planner** — Renamed *Week* in the interface; keeps its 7 columns, loses per-day card chrome, gains a real day selection and an empty-state that reads as intentional quiet.
- **Habits** — Keeps the heat map and streak numbers; loses the shared manual-minutes input (one field per habit) and gains one-click logging.
- **Weekly review** — Same three sections; the header names both weeks explicitly (planning week / reviewed week) instead of one week plus a parenthetical; saves become debounced and confirmed.
- **Monthly finance** — Layout unchanged in substance (it is already the most table-native screen); gains the shared type ladder, hairline borders and visible save state.
- **Projects** — Repainted onto the single palette and the shared table style; the screen stops looking like a different product.
- **Calendar** — No change: the app has no live calendar surface (`Calendar.jsx` is dead), so this concept neither adds nor removes one.

### Build cost & scope

**Size: S–M. Incremental, not a rewrite.** Nothing changes in the API, the database, `src/api.js`, `src/utils/*`, or the server. The work is a token layer plus a shell change plus repainting the surfaces that carry the most reading: the global stylesheets (`index.css`, `App.css`), `Sidebar` (→ top strip), `TodayView`, `PlannerHabitsPanel`, `DailyPlanner`, `MiniWeekBar`, `DayColumn`, `WeeklyReview`, `MonthlyReview`, `HabitTracker`, `HabitHeatmap`, `ProjectsView`, `TaskModal`, `BacklogSidebar` and the three small popovers. **Roughly 6–9 work sessions**, each one shippable on its own (tokens → shell → Today → week → habits → review/finance → modal and popovers → dead-code deletion). Untouched: `WeeklyObjectives`, `YearlyGoals`, `FinancialCards`, `HabitModal`, `ProjectModal`, `RichTextEditor`, `DailyWorkflow` (they inherit the token layer and need only a pass at the end), plus the four dead components, which are deleted rather than restyled. Deleting the dead stylesheets removes 1,828 of 7,719 CSS lines before the work starts (F11).

### What must not regress

`todayOrder` and its `sortOrder` sync (`src/App.jsx:202-211`); Monday-start week windows and the `weekStart − 1` rule for the reviewed week (ADR-005); recurring-task semantics including `statusOverrides`/`statusFromOverrides` (`src/App.jsx:152-184`); `descriptionImages` and the finance photo gallery with its 8 MB cap and read-only past months; the WORK-toggle weekly-review area if that work lands; the live `data/app.db`. The concept must also preserve the one behaviour that must survive being moved: the pure-text cleanup template and the goal → objectives bridge, including its replacement warning (`src/components/WeeklyReview.jsx:507-539`).

### Visual mood keywords & light/dark expectation

Light-first, and only light at launch. Paper, not glass: warm-neutral background, ink text, generous space, one recessive accent that behaves like a marker rather than a highlight. Type does the work — fewer weights, more space between blocks, letterspacing opened only on small labels. Borders are hairlines; shadows are effectively absent, reserved for the two genuine overlays (modals, popovers). Motion is limited to state change under 150ms and never decorative. Dark mode is reached later by swapping the same tokens on a "follow the system" setting; the concept is designed so that is a token swap and not a redesign, which is the main reason to build the token layer first.

## 8. Concept B — Timeline Studio

*Interactive and timeline-driven: drag-and-drop time-blocking, a split focus between the week and the day, and rich micro-interactions. The most ambitious of the three and the biggest departure from the reference brief.*

### Layout idea

At 1440×900: a dark canvas. A narrow left icon rail (about 56px) holds the destinations as icons with keyboard hints. The main area is a genuine time axis: seven day columns across the full width, with hour rows running vertically from early morning to late night, so the week's shape is legible without reading a single title. Blocks are positioned and sized by time, coloured by project at low saturation. A persistent left tray (about 280px) holds the unscheduled backlog as draggable chips, and a persistent bottom bar (about 64px) is the "day lens": the current hour, the current block, and a three-button peek — start, complete, defer — for whatever is now. Clicking any block opens an inline split editor on the right rather than a modal. The habit rail becomes a bottom-left cluster of 8 small day-dots you can click directly. Empty time is empty space with a faint hour rule, which is exactly the signal the user needs when deciding where to put something.

### Navigation flow (cold open → "what do I do now")

Cold open is **this week's timeline, auto-scrolled so today's column and the current hour are in view**. Steps:

- **Add a task**: type into the always-visible tray input at the top of the unscheduled tray, press Enter (**1 action**); it appears as a chip. Dragging a chip into a time slot (**1 drag**) both schedules and times it in one gesture — replacing today's "open an 11-field modal, then drag the card, then set a time separately".
- **Move a task onto today**: drag the chip into today's column at the intended hour. **1 drag.** Or press the day-lens "Today" action on the current block.
- **Log a habit**: click the habit's dot in the bottom-left cluster. **1 click**; a second click on the same dot opens a small duration entry.
- **Get to today's plan**: it is the cold open at week zoom; pressing the day-lens zoom button goes to a single-day view. **0–1 clicks.**

### Key highlights

- Time becomes the primary axis and every task with a time is placed on it; tasks with durations render as blocks you can resize.
- Drag-to-create: dragging on empty grid space creates a block with start and duration already set.
- The three conflicting time fields collapse into one model in the interface (a start, an end, and the estimate derived from them), with a migration decision needed before build (see cost).
- A drag ghost with a live time label, so the user sees the target hour before releasing rather than after.
- Keyboard parity for every drag: select a chip with the keys, move it with arrow keys, commit with Enter, and an undo on the last move.
- The day lens answers "what now" without navigation: current block, minutes remaining, next block, and single-tap start/complete/defer.
- Habit logging is a dot matrix, so the nightly ritual is eight clicks in one place rather than eight popover round trips.
- Deck-style project tinting: colour at low saturation with a legible label, so the week reads as shape not noise.

### Feature implications

- **Today** — Not a separate destination: it is the day lens at day zoom. The list still exists but as the day's sidebar, not the main event.
- **Planner** — Becomes the primary surface and is genuinely rebuilt: the week grid gains a real time axis and blocks replace cards.
- **Habits** — Becomes a persistent cluster on the timeline rather than a view you visit; the full heat map moves behind the cluster.
- **Weekly review** — Keeps its three sections but reads from the timeline: "what did the week actually contain" is answerable from the grid the review sits beside.
- **Monthly finance** — Largely untouched; it is a month-keyed document, not a time surface, and forcing it onto the timeline would be decoration.
- **Projects** — Gains a colour discipline (project colour becomes the block tint), so project colour finally means something in the interface.
- **Calendar** — Explicitly in scope: the concept is the app growing the calendar surface it currently only has in dead code, which is a product decision, not a restyle.

### Build cost & scope

**Size: L. Roughly a third of the front end is a rebuild rather than a restyle.** Rebuilt: `DailyPlanner`, `DayColumn`, `MiniWeekBar` and `DailyTimeline` (folded into one timeline surface with an hour axis, block rendering and drag/resize), `TodayView` (reduced to the day lens plus list), `BacklogSidebar` (becomes the draggable tray), `App.jsx`'s shell, and `TaskModal` for the time fields. Untouched: `WeeklyReview`, `MonthlyReview`, `FinancialCards`, `ProjectsView`, `YearlyGoals`, `WeeklyObjectives`, `HabitModal`, `ProjectModal`, `RichTextEditor`, and **all** server code, routes and the database. **Roughly 14–20 work sessions**, and it cannot be shipped in small user-visible slices with the same ease as Concept A — the shell change is the change. One pre-work decision is mandatory and is not a UI decision: `scheduledTime`, `startTime`/`endTime` and `estimatedMinutes` must be reconciled into one time model (F30, `src/components/DayColumn.jsx:235-245` for how they render, `src/components/TaskModal.jsx:460-497` for where they are entered), otherwise the timeline inherits all three. A second: whether drag-only actions may remain the primary means of scheduling, given they currently have no keyboard or touch path (F10, §4.2).

### What must not regress

Everything in Concept A's list, plus the two things this concept is most likely to break: the ordering model must stay compatible with `todayOrder` (the array is persisted per day as string keys, so any timeline ordering has to write *through* it, not around it), and recurring-task instances must remain individually movable and completable without corrupting the base row's overrides (`src/App.jsx:152-184`). The 500-instance cap in the recurrence generator (`src/utils/recurrence.js:109-120`) must be respected: a week-wide timeline asks for more instances per render than a day column does.

### Visual mood keywords & light/dark expectation

Dark-first. Cinema, console, control room: a deep neutral ground with low-saturation project tints and high-contrast type; blocks separated by tone rather than borders; a single bright now-line as the only saturated element on screen. Motion is part of the language — blocks ease into place, drags show a live label, the now-line advances — but it must be short and interruptible, and it must be suppressible for reduced-motion. Because the canvas is dark-first, the light mode is the derived one, reached by a token swap if it is built at all; a light version of a dark timeline design tends to look washed out, so light mode should be treated as a separate design exercise rather than an automatic inverse.

## 9. Concept C — Command Deck

*Command and keyboard-first: a command palette as the primary navigation, instant capture from anywhere, keyboard navigation everywhere. The smallest visual change of the three and the largest change to how the app is operated.*

### Layout idea

At 1440×900: a light, functional interface with a narrow left icon rail (about 48px) holding the destinations, and one content pane taking the rest — plus, unlike today, no second header repeating the active destination. A permanent command bar sits at the bottom of the window (about 44px tall), always visible, always typeable, showing a faint hint of the last action taken. The day is a dense but ordered list: every task one line, with a monospace right column carrying the numbers (estimate, time, project code) so durations line up and can be compared at a glance — the same reason the finance table works today. Above the list, a one-line "now" strip carries the current block, minutes remaining and the next item. Selected rows are marked with a left rule and a tint, never with a card. Numbers everywhere use tabular figures. Panels do not stack: picking a row expands it in place, and only genuinely modal work (recurrence rules, photos) opens a dialog.

### Navigation flow (cold open → "what do I do now")

Cold open is **Today with the cursor already on the first unfinished item**. Steps:

- **Add a task**: `Ctrl+K` (the palette the concept is named for) or `/` focuses the command bar; type the title; Enter. **1 keystroke, type, 1 keystroke** — no navigation, from any view.
- **Move a task onto today**: with the row selected, `t` sets the date to today; `⇧T` opens a small date field. **1 keystroke.** For a task in the backlog, open the palette, type its first letters, press Enter to jump to it, then `t`.
- **Log a habit**: `h` opens the habit list in the palette; typing a habit's name and pressing Enter logs it done for today, with `+15`-style suffixes accepted for a duration. **2 keystrokes + Enter.**
- **Get to today's plan**: `g` then `d`, or `Ctrl+K` → type `today` → Enter. **2–3 keystrokes**, with no mouse.

### Key highlights

- One command palette reaches every destination, every task by fuzzy title, every habit by name, and every action ("defer to tomorrow", "log 30 minutes guitar", "new project").
- A single global capture line: it exists on every view and is the same control the palette uses, so there is one place to type and one mental model.
- List navigation with `j`/`k`, completion with `x`, defer with `t`, edit-in-place with `e`, and undo with `Ctrl+Z` for the last action — replacing 12 hover-only icons (F10).
- The displayed shortcut for each action is discoverable: a palette footer lists the current context's keys, and every icon control carries its key as a suffix instead of relying on a browser tooltip (F38).
- Tabular, right-aligned numbers in one monospace column, so estimates and durations are comparable down the page instead of scattered across badges.
- All destructive actions route through one undo-toast mechanism instead of two different risk models (F27, F28), and native dialogs are gone.
- The command bar doubles as a status line: "Saved 14:32", "Saved with errors — retry", so silent saves end (F26).

### Feature implications

- **Today** — Same content, denser and keyboard-operable; becomes the cold open with a cursor already placed.
- **Planner** — Keeps the 7-day grid but every cell and card becomes reachable by keyboard; the week's paging and the dead day buttons are replaced by real navigation.
- **Habits** — One-keystroke logging from anywhere; the heat map becomes a read view, not the logging mechanism.
- **Weekly review** — The three sections gain keyboard traversal and the section state is explicit (the current collapse state lives in local storage on a key per section, `src/components/WeeklyReview.jsx:249-264`); the two-week distinction gets a visible toggle rather than a parenthetical.
- **Monthly finance** — Already table-based; gains tabular numerals, a keyboard path between payment fields, and a per-cell save indicator instead of per-keystroke writes.
- **Projects** — Becomes fully command-driven (create, rename, recolour) and is repainted onto the shared palette; the table stays.
- **Calendar** — Unchanged: there is no live calendar surface to command.

### Build cost & scope

**Size: M. Incremental, but with two genuinely new pieces.** New: the command palette (a single overlay with a fuzzy list over tasks, habits, projects, views and actions) and a global keyboard layer (shortcut registry, focus management, undo stack). Restyled or rebuilt: `Sidebar` (→ icon rail), `App.jsx`'s shell and its capture wiring, `TodayView` (dense list, selection model), `DayColumn`, `PlannerHabitsPanel`, `TaskModal` (splitting the always-visible form into inline quick-edit plus an explicit "more fields" mode), the two long-form list surfaces in `WeeklyReview` and the payment table in `MonthlyReview`. Untouched: `HabitHeatmap`, `HabitModal`, `YearlyGoals`, `WeeklyObjectives`, `FinancialCards`, `ProjectsView`, `RichTextEditor`, `ProjectModal`, and all server code, routes and the database. **Roughly 9–13 work sessions.** The keyboard layer should land first and alone (focus visibility plus list navigation), because that is the highest-value slice and it does not depend on the palette.

### What must not regress

Everything in Concept A's list, plus the specific risk of a keyboard-focused interface: **focus must never be trapped or lost**. Today's modal and lightbox only handle Escape by attaching document listeners (`src/components/TaskModal.jsx:136-146`, `src/components/YearlyGoals.jsx:131-142`), and the single `tabIndex` in the app is on a paste target (`src/components/MonthlyReview.jsx:733`) — so the paste-a-photo flow is the one place where a global key layer could silently steal a keystroke, and it must keep working. Inline editing must not remove the per-field save semantics that already work (notes on blur, `src/components/MonthlyReview.jsx:700`).

### Visual mood keywords & light/dark expectation

Light-first, but utilitarian rather than calm: a workbench, a control panel. Neutral ground, high-contrast ink, tabular monospace for all numbers, one accent used only for the current selection and the active command. Borders do the separating; elevation appears only for the palette and dialogs. Motion is minimal and functional — a row highlights, a list filters, nothing animates for effect. Dark mode is a genuine second requirement here rather than an afterthought, because a keyboard-driven app is often operated in the evening and the palette must read as clearly against a dark ground; the token layer should therefore be built for two modes from the start, with the light mode as the default and the system preference as the switch.

## 10. Recommendation + what we could not verify

### Recommendation: Concept A — Calm Canvas

**Why, against §5.** The scorecard's two lowest pillars are keyboard affordance (1) and flow state, cognitive load, time clarity and hierarchy (2 each). Concept A is the only one of the three that raises all six at the same time and does so on top of the cheapest possible change of the three: no data model is touched, no route changes, and it is the only concept that can ship as a series of independently useful slices from the first session. It fixes, in priority order: the cold open (`src/App.jsx:41`), the hidden-action problem (F10) by making reorder/edit/defer persistent text actions, the habit ritual (F22) by making one click sufficient, the per-keystroke write and the invisible save (F25, F26) with debounce plus a status line, the type ladder (F05), the palette split (F03/F04), the dead stylesheets (F11/F12) and the mobile dead end (F16), and it gives the week bar back its day selection (F20) rather than designing around a control that does nothing.

**What it does not fix, and why that is acceptable now.** It improves but does not solve time clarity: without a real axis, "where does this 90-minute block actually fit" stays a judgement (F18/F19). That is the strongest argument for Concept B, and it is a genuine product cost — but B requires a decision about the three competing time fields before any pixel is drawn, and it converts a third of the front end into a rebuild, which cannot happen while the app is in daily use. Concept C's keyboard layer is not a competing idea but a piece of engineering discipline that should be taken regardless: a visible focus style and a small shortcut set belong in Concept A's first two sessions, and the command palette is a natural third slice once the shell is calm (it is the mechanism that finally makes "capture from anywhere" one keystroke). In short: **build A, fold in C's focus-and-shortcut discipline as a copy-and-paste-level addition, and keep B's timeline as the next initiative after the time-field question is settled with an ADR.**

**Which concept departs most from Anderson's own design reference** (`.opencode/design-references/notion-stripe-2026.md`): **Concept B — Timeline Studio.** The reference asks for a light neutral canvas, one accent reserved for state, hairline borders over shadows, restraint at display sizes, tables over charts, and 24–48px of breathing room; B is dark-first, colour-coded by project, motion-led and dense by construction. Concept C departs moderately (monospace numerals and a persistent command bar are not in the reference, but its restraint and table-first instincts are). Concept A is the closest of the three on purpose — and because the reference is the craft floor rather than a target, A should also not be allowed to collapse *into* it: the differentiator A must keep is that it is a **day**, not a document — the habit rail, the hours strip and the single capture line are the parts that make it DayFrame and not a Notion page.
